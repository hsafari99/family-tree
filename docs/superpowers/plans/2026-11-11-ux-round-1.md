# UX Round 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Act on the first round of user feedback (19 items): form polish and two bugs, a two-column Account page, a calmer person panel with better ways to add and re-link parents and siblings, couples that always sit together on the canvas, a collapsible panel on the left, saved partner order, and tidy People, Trash and Members lists.

**Architecture:**
- **Forms (web only):** `Field` grows a show/hide toggle for passwords and a `data-field` hook. A new `ErrorSummary` lists every field error and moves focus to the field. `FuzzyDateField` gets a precision picker and a native calendar for exact days. The stored fuzzy-date shape and its API schema stay as they are.
- **Data model:** one migration.
  - `unions.parents_unknown`: a union with no partners that groups siblings whose parents aren't recorded. The `unions_has_partner` CHECK is relaxed to allow exactly this.
  - `unions.partner_a_order` and `unions.partner_b_order`: each partner's own saved position for this union among their partners. Each partner orders their own unions, so two people's orders never fight.
  Every place that assumes a union has a partner is updated: the loaders, branch, kinship, the relationship route, deletion planning (person, link, union and re-parent), Trash labels and erase, the graph view, the canvas mapping and the export.
- **New API routes** (all after the global rate limiter, all audited, and all following the structural-write lock order):
  - `POST …/parent-child/:linkId/reparent`
  - `POST …/unions/:unionId/swap-partners`
  - `POST …/persons/:personId/union-order`
  Plus two additive request fields:
  - `coParent` on create-person, for adding both parents in one step.
  - `unionId: null` on relative links, meaning "start a new pair of parents".
- **Canvas:** a post-layout pass, `seatCouples`, puts partners next to each other in every row and keeps sibling order between couple groups. The side panel moves left and can be collapsed, with the state remembered. Child edges can be dragged onto a union dot to re-link them.
- **Lists:** compact rows and buttons in the People and Trash lists. Members becomes a real table that stacks on mobile.

**Tech Stack:** Fastify 5.12.8, Drizzle 0.45.4, Postgres 17, Zod 4.6.7, React 19.3.1, react-router 8.5.1, `@xyflow/react` 12.12.0, `elkjs` 0.12.0, Vitest 5.1.0, Playwright (as pinned), Vite **8.3.6**. **No new dependencies.**

## Decisions taken in this plan

1. **Parents-unknown unions (#11).**
   - **The current model:** the `unions_has_partner` CHECK forbids a union with no partners. Spec §3 says "a child with both parents unknown simply has no `parent_child` row". So today two siblings with unknown parents can't be recorded at all.
   - **What we do:** relax the CHECK to `partner_a_id is not null or partner_b_id is not null or parents_unknown`, and add `parents_unknown boolean not null default false`. The sibling route creates such a union and links both children to it.
   - **Why a flag rather than dropping the CHECK:** the database still rejects accidental partnerless unions. Several paths empty partner slots: deletion, restore and erase. Without the CHECK, a bug in any of them would leave invisible empty unions. The flag says "empty on purpose".
   - **The flag never changes:**
     - If a parent is added later, they fill an empty slot of that union, so the siblings share the new parent.
     - If that parent is deleted, the union survives (their slot is emptied), so the siblings stay siblings.
     - **It is never left childless.** Every path that can take its last live child link away also removes the union (only while it has no partner; once a parent fills a slot it is an ordinary single-parent union):
       - deleting the last child (`planPersonDeletion`): the union goes in the same batch;
       - removing the last child link (`planLinkDeletion`): the union goes in the same batch;
       - re-parenting the last child elsewhere (Task 15): the union is soft-deleted into the newest Trash batch that still holds one of its links (so restoring that batch brings the siblings back together), or hard-deleted when no trashed row refers to it, since it then holds nothing;
       - deleting the union itself ("Remove", `planUnionDeletion`): the union and all its child links go in one batch, labelled "Siblings with unknown parents" in Trash. The steward check uses the children as the ends (`touchedPersonIds`), so an empty partner list never passes vacuously;
       - erasing a batch that held a person in one of its slots: the slot is emptied, never cascaded (the partner FK is `ON DELETE CASCADE`), so the siblings stay together.
   - **Why not a placeholder "Unknown" person:** it would pollute search, branch, export and counts.
   - **Every place that assumed a partner:**
     - the CHECK;
     - `loadLiveGraph`, `loadGraphRows` and the export loader, which drop partnerless unions;
     - `branchOf` and `branchQuery`, where the union becomes a virtual parent so siblings share a branch;
     - `kinEdges`, where the union is a virtual parent step marked `virtual`, so the wording still says "sister";
     - `planPersonDeletion` and `planLinkDeletion`;
     - the re-parent route and `restoreBatch` (Task 15);
     - `GET …/relationship` (`routes/search.ts`), which built `persons` from every step's `personId` and would 500 on a virtual step's union id;
     - Trash: `rootOf` and the batch detail (the "Siblings with unknown parents" label), and the erase slot-emptying;
     - `visibleRelations`;
     - `chooseUnion` and `attachRelative`;
     - the `canEdit` ends in `buildTreeGraph` (partners, or the children when there are none);
     - `hasParents`;
     - `graphToFlow`, which skipped zero-partner unions (`partnerIds.length === 0`);
     - `assignGenerations`, where siblings share a row;
     - `toElkGraph`, whose partition used `Math.min` over the partners;
     - `UnionPanel`;
     - the Relations tab, with the label "Parents unknown".
     
     The GEDCOM writer already copes: it writes a FAM with only CHIL lines.
2. **Partners adjacent (#14).** ELK's model has nothing that ties two partners together. Partner edges go *down* to the union dot, so a sibling between partners crosses nothing, and crossing minimisation doesn't care.
   - **Rejected:**
     - Compound nodes: they break the partition-per-generation scheme and multi-partner chains.
     - ELK's `forceNodeModelOrder`: it gives up crossing minimisation across families.
   - **Chosen:** keep ELK for rows and rough x positions. A pure post-pass, `seatCouples`, in `applyElkLayout`:
     1. Groups each row's people into couple chains, with partners joined.
     2. Orders the chains by the leftmost member who is someone's child. That keeps sibling birth and `sibling_order` order *between* couple groups.
     3. Seats each chain's members side by side near ELK's mean x for the chain, pushing right to avoid overlaps.
   - **Inside a chain:**
     - A two-person couple goes `partner_a`, then `partner_b`. "Swap sides" (#16) flips this.
     - A person with several partners sits in the middle. Their unions, in the hub's own saved order (`partner_a_order` when the hub is partner a, else `partner_b_order`), go first-left, second-right, then alternate outwards.
   - React Flow draws edges from node positions, so moving nodes after ELK is safe. The union-dot centring that already exists runs after the pass.
   - **Limit:** with three or more partners, only two can touch the person. The plan says so in the README.
3. **Re-parenting (#13).** It updates `parent_child.union_id` in place. The link id and kind stay the same, and nothing goes to Trash.
   - The rule is a new `can()` action, `link.reparent`:
     - When the move keeps every current parent (`{X}` → `{X, Y}`), the old side needs `relation.edit`-style scope: owner, editor, or a steward with one end in scope.
     - When it drops a parent, the old side needs `relation.delete` rights: owner, or a steward with *every* end in scope. Editors can't delete relations, so they can't detach a parent this way either.
     - The new side always needs `relation.add` scope.
   - This is "stewards need both unions in scope", made precise.
4. **Adding parents (#9).**
   - `relativeLinkSchema.unionId` now also accepts `null`, meaning "start a new pair of parents". Today a blank choice silently joins the only open union, so "Start a new pair of parents" didn't do what it said.
   - `createPersonSchema.coParent` (`{ person }` or `{ personId }`) adds a second parent into the new union in the same transaction.
   - "Add as child of X and Y" is the re-parent route.
5. **Partner order (#16).**
   - **Left/right within a couple:** swap `partner_a_id` and `partner_b_id`. This needs no column. Only a union with both partners live can be swapped, so no pending Trash slot can point at the wrong letter: a restore into a filled slot already fails as a conflict.
   - **The order of a person's unions:** two new columns, `unions.partner_a_order` and `unions.partner_b_order`. Each belongs to that slot's partner, so David ordering his partners never changes Laura's order of hers. Reads always use the person's own slot. "Swap sides" swaps the order columns together with the partner slots, so each person keeps their order. Filling an empty slot (a new parent or partner) sets that slot's order to null; a restore puts the person back into the same slot with their order untouched.
   - **Not allowed:** free reordering across families. ELK owns the layout, and a saved x position would fight it on every change. The spec already rules out free dragging (§1 non-goals, §6). Only siblings within a union, partners within a couple, and a person's unions can be reordered.
6. **The death-place bug (#8).**
   - **Hypothesis**, to be confirmed by the failing test in Task 7: on a living person, saving a death place in the Places tab fails. The API's `personConsistencyErrors` returns `isLiving: ["Someone with death details can't be marked as living"]`, the Places tab has no "Living" field, and the web shows only "Check the details and try again".
   - **The fix:**
     - The Places form offers "Mark as deceased" when a living person gets a death place, and sends `isLiving: false` with it.
     - Separately, every form maps server field keys onto its own fields, or onto the summary when no field shows them.
7. **Account (#6).**
   - Routes: `/account` and `/account/:section`, where the section is `profile`, `password`, `two-step`, `google` or `delete`. An unknown section gets the 404 page.
   - **Desktop (720px and up):** the nav on the left and the section on the right; `/account` shows Profile.
   - **Mobile:** `/account` shows only the list; a section page has a "Back to account" link.
   - Google's return URL becomes `/account/google?google=connected`.
8. **"Related to" (#10).** Verified in the code: the "as their" select in Add person already lists Partner (`RELATIVE_ROLES`), but it only renders once a person is picked (`{to && …}`, `AddPersonForm.tsx` about line 137), and the person field is labelled "Connect to". So the user never saw a Partner choice.
   - The person field is renamed "Related to", and a "Relationship" select is always rendered next to it, disabled until a person is chosen.
   - Its options read as a sentence with the chosen name: "Parent of Ann Hale", "Child of Ann Hale", "Partner or spouse of Ann Hale", "Sibling of Ann Hale" ("Parent of …" and so on while no one is chosen). "Partner or spouse of" shows the union type and status choices.
9. **People list (#17).** Verified in the code: `PeopleList` renders links only. The full-width buttons the user saw under the people list are TreePage's owner "Tree settings" forms (Rename, Starting person), stretched by `form { display: grid }`. Task 1 fixes them for every form (`form > :is(button, .confirm) { justify-self: start }`). Task 28 still gives the list a tidy row layout with a compact "Show on tree" button, and a shared `.compact` button style.
10. **One migration** for the round, holding the three columns. `partner_a_order` and `partner_b_order` are first used in Batch 4. The migration is **not reversible**: once a parents-unknown union exists, the old CHECK can't be put back, so like the repo's other migrations it has no down script. Generate it with drizzle-kit and don't hand-number it: it follows whatever `main` has by then (`0009_…` if 2FA-move's `0008` is merged).

```tsx
import { DATE_PRECISIONS, DATE_QUALIFIERS, type DatePrecision, type DateQualifier, type FuzzyDate, precisionOf } from '@family-tree/shared';
import { useId } from 'react';
import { QUALIFIER_LABEL } from '../trees/format';

export interface FuzzyDraft {
  qualifier: DateQualifier;
  precision: DatePrecision;
  /** day: YYYY-MM-DD; month: "YYYY-MM" (either part may be blank while typing); year: YYYY. */
  date1: string;
  date2: string;
}

const PRECISION_LABEL: Record<DatePrecision, string> = {
  day: 'Exact day',
  month: 'Month and year',
  year: 'Year only',
};
const MONTHS = ['January', 'February', 'March', 'April', 'May', 'June', 'July', 'August', 'September', 'October', 'November', 'December'];

export const toDraft = (d: FuzzyDate | null): FuzzyDraft =>
  d
    ? { qualifier: d.qualifier, precision: precisionOf(d.date1), date1: d.date1, date2: d.date2 ?? '' }
    : { qualifier: 'exact', precision: 'day', date1: '', date2: '' };

const cut = (s: string, p: DatePrecision) => (p === 'year' ? s.slice(0, 4) : p === 'month' ? s.slice(0, 7) : s);
export function withPrecision(d: FuzzyDraft, precision: DatePrecision): FuzzyDraft {
  // Going finer can't invent a month or day: day <- month/year starts the calendar empty.
  const fit = (s: string) => (precision === 'day' && s.length < 10 ? '' : cut(s, precision));
  return { ...d, precision, date1: fit(d.date1), date2: fit(d.date2) };
}

const blank = (s: string) => s.replace(/-/g, '').trim() === '';
function partError(s: string, p: DatePrecision): string | null {
  if (p === 'day') return /^\d{4}-\d{2}-\d{2}$/.test(s) ? null : 'Pick a date';
  const [y = '', m = ''] = s.split('-');
  if (!/^\d{4}$/.test(y)) return 'Enter a 4-digit year, like 1950';
  if (p === 'month' && !/^\d{2}$/.test(m)) return 'Choose a month';
  return null;
}
/** Our own message for an incomplete draft, or null (the schema then checks real dates). */
export function draftError(d: FuzzyDraft): string | null {
  if (blank(d.date1)) return null;
  const first = partError(d.date1, d.precision);
  if (first) return first;
  if (d.qualifier !== 'between') return null;
  if (blank(d.date2)) return 'Enter the second date';
  return partError(d.date2, d.precision);
}

/** The value to validate with fuzzyDateSchema: null when no date is typed. */
export function fromDraft(d: FuzzyDraft): unknown {
  if (blank(d.date1)) return null;
  return d.qualifier === 'between'
    ? { qualifier: d.qualifier, date1: d.date1, date2: d.date2 }
    : { qualifier: d.qualifier, date1: d.date1 };
}

function DateControl({ id, label, precision, value, onChange, describedBy, invalid }: {
  id: string; label: string; precision: DatePrecision; value: string;
  onChange: (v: string) => void; describedBy: string; invalid: boolean;
}) {
  const common = { 'aria-describedby': describedBy, 'aria-invalid': invalid || undefined } as const;
  if (precision === 'day') {
    return (
      <>
        <label htmlFor={id}>{label}</label>
        <input id={id} type="date" value={value} onChange={(e) => onChange(e.target.value)} {...common} />
      </>
    );
  }
  const [y = '', m = ''] = value.split('-');
  const join = (yy: string, mm: string) => (precision === 'year' ? yy : yy === '' && mm === '' ? '' : `${yy}-${mm}`);
  // With one control, the year input carries the outer label ("Date", "From", "To").
  const yearLabel = precision === 'year' ? label : 'Year';
  return (
    <div className="date-parts" role={precision === 'month' ? 'group' : undefined} aria-label={precision === 'month' ? label : undefined}>
      <span>
        <label htmlFor={`${id}-y`}>{yearLabel}</label>
        <input id={`${id}-y`} inputMode="numeric" maxLength={4} value={y} onChange={(e) => onChange(join(e.target.value.trim(), m))} {...common} />
      </span>
      {precision === 'month' && (
        <span>
          <label htmlFor={`${id}-m`}>Month</label>
          <select id={`${id}-m`} value={m} onChange={(e) => onChange(join(y, e.target.value))} {...common}>
            <option value="">Month…</option>
            {MONTHS.map((name, i) => (
              <option key={name} value={String(i + 1).padStart(2, '0')}>{name}</option>
            ))}
          </select>
        </span>
      )}
    </div>
  );
}

export function FuzzyDateField({ label, name, value, onChange, error }: {
  label: string;
  /** The form field key (birthDate, …): the error summary focuses it. */
  name: string;
  value: FuzzyDraft;
  onChange: (v: FuzzyDraft) => void;
  error?: string | undefined;
}) {
  const id = useId();
  const describedBy = error ? `${id}-error` : '';
  const between = value.qualifier === 'between';
  return (
    <fieldset className="field fuzzy-date" aria-describedby={describedBy || undefined}>
      <legend>{label}</legend>
      <div className="date-row">
        <span>
          <label htmlFor={`${id}-p`}>Precision</label>
          <select id={`${id}-p`} data-field={name} value={value.precision}
            onChange={(e) => onChange(withPrecision(value, e.target.value as DatePrecision))}>
            {DATE_PRECISIONS.map((p) => <option key={p} value={p}>{PRECISION_LABEL[p]}</option>)}
          </select>
        </span>
        <span>
          <label htmlFor={`${id}-q`}>How certain</label>
          <select id={`${id}-q`} value={value.qualifier}
            onChange={(e) => onChange({ ...value, qualifier: e.target.value as DateQualifier })}>
            {DATE_QUALIFIERS.map((q) => <option key={q} value={q}>{QUALIFIER_LABEL[q]}</option>)}
          </select>
        </span>
      </div>
      <DateControl id={`${id}-1`} label={between ? 'From' : 'Date'} precision={value.precision}
        value={value.date1} onChange={(date1) => onChange({ ...value, date1 })} describedBy={describedBy} invalid={!!error} />
      {between && (
        <DateControl id={`${id}-2`} label="To" precision={value.precision}
          value={value.date2} onChange={(date2) => onChange({ ...value, date2 })} describedBy={describedBy} invalid={!!error} />
      )}
      {error && <p id={`${id}-error`} className="field-error">{error}</p>}
    </fieldset>
  );
}
```

```tsx
  const key = entries.map(([k, m]) => `${k}:${m}`).join('|');
  useEffect(() => {
    if (key) ref.current?.focus();
  }, [key]);
  if (entries.length === 0) return null;
  const focusField = (k: string) => {
    const form = ref.current?.closest('form') ?? document;
    form.querySelector<HTMLElement>(`[data-field="${CSS.escape(k)}"], [name="${CSS.escape(k)}"]`)?.focus();
  };
  return (
    <div role="alert" className="error error-summary" tabIndex={-1} ref={ref}>
      <p>Check these and try again:</p>
      <ul>
        {entries.map(([k, m]) => (
          <li key={k}>
            {labels[k] ? (
              <button type="button" className="link" onClick={() => focusField(k)}>
                {labels[k]}: {m}
              </button>
            ) : (
              m
            )}
          </li>
        ))}
      </ul>
    </div>
  );
}

/** Server field keys -> this form's errors, with fixed text only (global rule). */
export function serverFieldErrors(
  keys: readonly string[],
  map: Record<string, { field: string; message: string }>,
): FieldErrors {
  const out: FieldErrors = {};
  for (const k of keys) {
    const hit = map[k];
    if (hit) out[hit.field] ??= hit.message;
    else out[''] ??= MESSAGES.checkDetails;
  }
  return out;
}
```

```tsx
// MenuButton.tsx
import { type KeyboardEvent, useEffect, useId, useRef, useState } from 'react';

export interface MenuItem {
  label: string;
  onSelect: () => void;
  danger?: boolean;
  disabled?: boolean;
}

/** A "⋯" menu (WAI-ARIA menu button) for a row's secondary actions (#7, #12). */
export function MenuButton({ label, items, text = '⋯' }: { label: string; items: MenuItem[]; text?: string }) {
  const id = useId();
  const [open, setOpen] = useState(false);
  const trigger = useRef<HTMLButtonElement>(null);
  const menu = useRef<HTMLUListElement>(null);
  const focusItem = (i: number) => {
    const els = menu.current?.querySelectorAll<HTMLButtonElement>('[role="menuitem"]:not(:disabled)');
    if (!els || els.length === 0) return;
    els[(i + els.length) % els.length]!.focus();
  };
  const close = (refocus: boolean) => {
    setOpen(false);
    if (refocus) trigger.current?.focus();
  };
  useEffect(() => {
    if (!open) return;
    focusItem(0);
    const onDown = (e: MouseEvent) => {
      if (!menu.current?.contains(e.target as Node) && e.target !== trigger.current) setOpen(false);
    };
    document.addEventListener('mousedown', onDown);
    return () => document.removeEventListener('mousedown', onDown);
  }, [open]);
  const onMenuKey = (e: KeyboardEvent) => {
    const els = [...(menu.current?.querySelectorAll<HTMLButtonElement>('[role="menuitem"]:not(:disabled)') ?? [])];
    const at = els.indexOf(document.activeElement as HTMLButtonElement);
    if (e.key === 'ArrowDown') { e.preventDefault(); focusItem(at + 1); }
    else if (e.key === 'ArrowUp') { e.preventDefault(); focusItem(at - 1); }
    else if (e.key === 'Home') { e.preventDefault(); focusItem(0); }
    else if (e.key === 'End') { e.preventDefault(); focusItem(els.length - 1); }
    else if (e.key === 'Escape') { e.preventDefault(); e.stopPropagation(); close(true); }
    else if (e.key === 'Tab') setOpen(false);
  };
  return (
    <span className="menu">
      <button ref={trigger} type="button" className="secondary compact menu-trigger"
        aria-label={label} aria-haspopup="menu" aria-expanded={open} aria-controls={open ? id : undefined}
        onClick={() => setOpen((o) => !o)}
        onKeyDown={(e) => { if (e.key === 'ArrowDown' || e.key === 'Enter' || e.key === ' ') { e.preventDefault(); setOpen(true); } }}>
        <span aria-hidden="true">{text}</span>
      </button>
      {open && (
        <ul id={id} role="menu" aria-label={label} ref={menu} className="menu-list" onKeyDown={onMenuKey}>
          {items.map((it) => (
            <li key={it.label} role="none">
              <button type="button" role="menuitem" tabIndex={-1} disabled={it.disabled}
                className={it.danger ? 'menu-item danger-text' : 'menu-item'}
                onClick={() => { close(true); it.onSelect(); }}>
                {it.label}
              </button>
            </li>
          ))}
        </ul>
      )}
    </span>
  );
}
```

```ts
// couples.ts
import { CARD_WIDTH } from './graph-to-flow';

export interface Couple {
  unionId: string;
  /** Node ids p:<id>, in slot order: a sits left of b unless the hub's union order says otherwise. */
  a: string;
  b: string;
  /** Each partner's own saved position for this union (partner_a_order, partner_b_order). */
  aOrder: number | null;
  bOrder: number | null;
}
type Pos = { x: number; y: number };

/**
 * Re-seats each row so partners sit side by side (brief #14, decision 2). ELK gives the rows and
 * rough x; this keeps each couple chain together, orders chains by their leftmost blood member
 * (so sibling order between families holds), and packs them without overlap near ELK's x.
 * Mutates `pos` and returns how far it moved each person (node id -> dx), so the caller can keep
 * union dots with their parents. `blood`: node ids of people shown as someone's child.
 */
export function seatCouples(pos: Map<string, Pos>, couples: readonly Couple[], blood: ReadonlySet<string>, gap: number): Map<string, number> {
  const moved = new Map<string, number>();
  const rowOf = (id: string) => Math.round(pos.get(id)!.y);
  const partners = new Map<string, Couple[]>();
  for (const c of couples) {
    if (!pos.has(c.a) || !pos.has(c.b) || rowOf(c.a) !== rowOf(c.b)) continue;
    for (const p of [c.a, c.b]) partners.set(p, [...(partners.get(p) ?? []), c]);
  }
  // Each person's unions in *their own* saved order (their slot's column), then by id.
  const orderFor = (c: Couple, p: string) => (c.a === p ? c.aOrder : c.bOrder) ?? Infinity;
  for (const [p, list] of partners) list.sort((x, y) => orderFor(x, p) - orderFor(y, p) || (x.unionId < y.unionId ? -1 : 1));
  const other = (c: Couple, p: string) => (c.a === p ? c.b : c.a);

  const rows = new Map<number, string[]>();
  for (const id of pos.keys()) if (id.startsWith('p:')) rows.set(rowOf(id), [...(rows.get(rowOf(id)) ?? []), id]);

  for (const ids of rows.values()) {
    ids.sort((m, n) => pos.get(m)!.x - pos.get(n)!.x);
    const seen = new Set<string>();
    const groups: string[][] = [];
    for (const start of ids) {
      if (seen.has(start)) continue;
      const comp: string[] = [];
      for (const q = [start]; q.length > 0; ) {
        const p = q.pop()!;
        if (seen.has(p)) continue;
        seen.add(p);
        comp.push(p);
        for (const c of partners.get(p) ?? []) q.push(other(c, p));
      }
      groups.push(chain(comp));
    }
    const meanX = (g: string[]) => g.reduce((s, p) => s + pos.get(p)!.x, 0) / g.length;
    const key = (g: string[]) => {
      const kin = g.filter((p) => blood.has(p)).map((p) => pos.get(p)!.x);
      return kin.length > 0 ? Math.min(...kin) : meanX(g);
    };
    groups.sort((g, h) => key(g) - key(h));
    let cursor = -Infinity;
    for (const g of groups) {
      const width = g.length * CARD_WIDTH + (g.length - 1) * gap;
      const left = Math.max(meanX(g) - (width - CARD_WIDTH) / 2, cursor);
      g.forEach((p, i) => {
        const x = left + i * (CARD_WIDTH + gap);
        const dx = x - pos.get(p)!.x;
        if (dx !== 0) moved.set(p, dx);
        pos.set(p, { x, y: pos.get(p)!.y });
      });
      cursor = left + width + gap;
    }
  }
  return moved;

  /** Left-to-right seats for one couple component. */
  function chain(comp: string[]): string[] {
    if (comp.length === 1) return comp;
    if (comp.length === 2) {
      const c = partners.get(comp[0]!)![0]!;
      return [c.a, c.b];
    }
    // The person with the most partners sits in the middle: first union left, second right, …
    const hub = [...comp].sort((m, n) => partners.get(n)!.length - partners.get(m)!.length || pos.get(m)!.x - pos.get(n)!.x)[0]!;
    const out = [hub];
    partners.get(hub)!.forEach((c, i) => (i % 2 === 0 ? out.unshift(other(c, hub)) : out.push(other(c, hub))));
    // Partners of partners go on the outside next to them, when that end is free.
    for (let placed = true; placed; ) {
      placed = false;
      for (const p of comp) {
        if (out.includes(p)) continue;
        const mate = (partners.get(p) ?? []).map((c) => other(c, p)).find((m) => out.includes(m));
        if (mate === undefined) continue;
        const at = out.indexOf(mate);
        if (at === 0) out.unshift(p);
        else if (at === out.length - 1) out.push(p);
        else out.splice(at + 1, 0, p); // three or more partners: only two can touch (decision 2)
        placed = true;
      }
    }
    return out;
  }
}
```

  The dot pass then places every kind of union dot, replacing the existing couple-only centring, so no dot is left where ELK put it once the people moved. Two dots can't simply follow their own rules independently: a parents-unknown dot (partition `2·childRow + 1`) shares a layer with the couple and one-partner dots of the row above, and a one-partner dot that just moved by its partner's dx can land on the re-centred couple dot beside it. So the pass puts them down in a fixed order and nudges any dot sideways off the ones already placed:

```ts
type Pos = { x: number; y: number };
/**
 * Places every union dot once seatCouples has moved the people (brief #11, #14). A couple's dot goes
 * midway between them; a one-partner dot under its partner's card (several fan out side by side); a
 * parents-unknown dot over its shown children. In that order, each dot is nudged sideways, in
 * steps, off any dot already placed in its layer. Mutates `pos`.
 */
function placeUnionDots(nodes: readonly CanvasNode[], laidOut: ElkNode, pos: Map<string, Pos>, gap: number): void {
  const centre = (id: string) => pos.get(id)!.x + CARD_WIDTH / 2;
  const step = UNION_SIZE + gap / 2;
  const placed: Pos[] = [];
  const clashes = (x: number, y: number) =>
    placed.some((q) => Math.abs(q.y - y) < UNION_SIZE && Math.abs(q.x - x) < step);
  const put = (id: string, want: number) => {
    const y = pos.get(id)!.y;
    const x0 = want - UNION_SIZE / 2;
    let x = x0;
    // +1, −1, +2, −2 … steps from where it wants to be, until it is clear.
    for (let k = 1; clashes(x, y); k++) x = x0 + Math.ceil(k / 2) * step * (k % 2 === 1 ? 1 : -1);
    const p = { x, y };
    pos.set(id, p);
    placed.push(p);
  };
  const shown = (id: string | null) => (id !== null && pos.has(`p:${id}`) ? `p:${id}` : null);
  const kidsOf = new Map<string, string[]>(); // union node id -> its shown children's node ids
  for (const e of laidOut.edges ?? []) {
    const [from, to] = [e.sources[0]!, e.targets[0]!];
    if (e.id.startsWith('child:') && pos.has(to)) kidsOf.set(from, [...(kidsOf.get(from) ?? []), to]);
  }
  const couples: [string, string, string][] = [];
  const singles = new Map<string, string[]>(); // partner node id -> their one-partner dots
  const unknown: string[] = [];
  for (const n of nodes) {
    if (n.type !== 'union' || !pos.has(n.id)) continue;
    const ps = [shown(n.data.union.partnerAId), shown(n.data.union.partnerBId)].filter((p) => p !== null);
    if (ps.length === 2) couples.push([n.id, ps[0]!, ps[1]!]);
    else if (ps.length === 1) singles.set(ps[0]!, [...(singles.get(ps[0]!) ?? []), n.id]);
    else unknown.push(n.id);
  }
  for (const [id, a, b] of couples) put(id, (centre(a) + centre(b)) / 2);
  // A card's centre is at least (CARD_WIDTH + gap) / 2 from any couple dot of its row, so up to five
  // dots fan out under one card before the nudge has anything to do.
  for (const [p, dots] of singles) dots.forEach((id, i) => put(id, centre(p) + (i - (dots.length - 1) / 2) * step));
  for (const id of unknown) {
    const kids = kidsOf.get(id) ?? [];
    put(id, kids.length > 0 ? kids.reduce((sum, k) => sum + centre(k), 0) / kids.length : pos.get(id)!.x + UNION_SIZE / 2);
  }
}
```

  `applyElkLayout` calls `placeUnionDots(nodes, laidOut, pos, gap)` right after `seatCouples`, with the same `gap`. `seatCouples` still returns its shifts (its unit tests read them), but the dot pass no longer needs them: a one-partner dot goes under its partner wherever they ended up. Children move only within their own row's packing, so their edges still come from their dot.

  - A parents-unknown dot whose wanted x falls on a couple dot in the same layer (same y) is nudged by one `step` to the right and no longer overlaps it; the couple dot stays exactly midway.
  - A one-partner dot whose partner's centre falls on a couple dot of a non-adjacent pair (a hub with three partners) is nudged off it, and still lies within the partner's card width.
